# Решения безопасности

## D-02. Проверка объекта, действия и состава ответа

**Контекст:** вошедший заявитель B может подставить номер обращения A; специалист S2 — номер назначения S1. Проверка только роли пропускает оба случая. Будущая заметка также может утечь в общей сериализации обращения. Связи: T-02, T-03, T-04 → SR-02, SR-03, SR-04.

**Решение:** идентичность берём из серверной сессии. При чтении запрос к БД включает предикат `author_id = user.id` для заявителя или `assignee_id = user.id` для специалиста. Тот же фильтр действует в списке. Чужой и отсутствующий номер дают одинаковый 404. DTO содержит только явно разрешённые поля; неизвестные поля входного JSON отклоняются. При создании автор берётся из сессии, состояние и время — из БД. Проверки выполняются на сервере при каждом запросе.

Целевая политика действий:

| Действие | Кто | Условие | Состав ответа / записи |
| --- | --- | --- | --- |
| Создать | Заявитель | Действительная сессия | Только тема и описание от клиента; начальное состояние `new` |
| Читать обращение | Автор или ответственный | Совпадает связь с объектом; любое состояние | Общие данные без внутренних заметок |
| Очередь (план) | Специалист | Только `new`, без ответственного | Только номер и время; содержание ещё закрыто |
| Принять (план) | Специалист | Свободное `new`, `expected_version=1` | Назначить текущего специалиста |
| Сообщение (план) | Автор / ответственный | Автор: `new` или `in_progress`; ответственный: `in_progress` | Автор и время от сервера |
| Заметка (план) | Ответственный | Запись только `in_progress`; чтение также после закрытия | Отдельный ресурс; доступ автора и S2 запрещён |
| Закрыть (план) | Ответственный | `in_progress`, непустое решение, актуальная версия | Добавить решение и событие, сохранить назначение |
| Открыть снова (план) | Автор | `closed`, непустая причина, актуальная версия | Добавить причину и событие; сохранить назначение |

**Обоснование:** скрытая кнопка или проверка роли в клиенте обходится прямым HTTP-запросом. Проверка связи с объектом в SQL ограничивает и карточку, и список. Раздельные DTO и ресурс заметок позволяют контролировать поля без фильтрации уже раскрытого ответа.

**Будущая проверка:** подготовить A/B/S1/S2, свободное и назначенное S1 обращение, заметку. Выполнить чтение карточки, списка, очереди и заметки каждым аккаунтом; подставить чужой номер и поля author/role/assignee/status. Ожидаем разрешение только по таблице, отсутствие текста заметки в любом ответе A/B/S2, очередь без темы и описания, неизменную БД при отказе. Повторить чтение после закрытия и открытия. Уже реализованная часть проверяется HTTP-тестами; очередь и заметки пока только план.

**Ограничения:** оператор БД доверенный и может обходить HTTP. Сейчас нет переназначения. При его добавлении политика и тесты должны пересматриваться.

## D-01. Пароли и отзываемые серверные сессии

**Контекст:** наличие заголовка не подтверждает личность; быстрый хеш позволяет дешёвый перебор копии БД. Связи: T-01, T-08 → SR-01, SR-08.

**Решение:** учебные роли готовит локальный seed. Пароли хранятся как Argon2id: 64 MiB, 3 прохода, p=1, случайная соль 16 байт, результат 32 байта. Алгоритм и параметры входят в сохранённую строку. Проверка допускает только выбранные параметры и длины, сравнивает результат за постоянное время. Неизвестный логин проходит такую же дорогую проверку фиктивного хеша. Одновременно допускаются четыре проверки, остальные запросы получают 429.

После успешного входа сервер выдаёт 32 случайных байта в base64url. База хранит SHA-256 токена, account_id и срок 8 часов; роль при каждом запросе читается из аккаунта. SHA-256 подходит для случайного 256-битного токена, но не для человеческого пароля. Выход удаляет текущую сессию. Повторный seed меняет пароли и отзывает сессии учебных аккаунтов, сохраняя обращения. Ошибка БД не даёт доступ. Ответы не кешируются; пароль и токен не пишутся в журналы.

**Обоснование и альтернативы:** Argon2id выбран для замедления перебора через память и вычисления. Параметры выше [минимального ориентира OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html); на целевом компьютере их ещё нужно измерить под нагрузкой. Выбрана серверная сессия, потому что немедленный выход и смена пароля требуют отзыва. Самодостаточный JWT уменьшает обращения к БД, но для немедленного отзыва всё равно нужна дополнительная серверная информация. Для небольшого локального API один запрос сессии проще. Bearer-токен выбран для CLI; браузерного интерфейса сейчас нет.

**Будущая проверка:** на A/B проверить правильный и неверный пароль, неизвестный логин, отсутствие/подмену токена, выход, срок сессии и отказ БД. Ожидаем 200 только для действительного входа, 401 для недействительной сессии, 503 при недоступной БД без личных данных. У одинакового пароля A/B хеши должны различаться, исходного пароля в базе нет. После seed прежние токены не работают, обращения остаются. Для будущего сетевого развёртывания измерить задержку и память, проверить TLS и лимиты повторных попыток; четыре слота ограничивают память, но не останавливают последовательный перебор.

**Ограничения:** сейчас HTTP разрешён только на loopback. Полученный токен даёт права до истечения/отзыва; безопасность клиента и ОС — допущение модели. Очистка истёкших строк сессий и полноценные лимиты входа будут нужны при долгом сетевом запуске.

## D-04. Параметризованный SQL и ограниченный ввод

**Контекст:** логин и тексты проходят от клиента до БД, а номер влияет на выбор объекта. Связь: T-07 → SR-07.

**Решение:** запросы написаны статически; значения передаются через `$1`, `$2` и следующие параметры pgx. Склейка SQL используется только для постоянных серверных фрагментов (список полей и предикат доступа), без пользовательского ввода. ID — положительный int64 из десятичных цифр; текст — UTF-8 без NUL, с пределом длины. JSON ограничен 32 KiB, неизвестные поля и дополнительные JSON-значения отклоняются. Допустимый текст с кавычками или SQL сохраняется как строка после стандартного JSON-декодирования, без SQL-интерпретации. Политика повторных ключей и Unicode описана в [API.md](API.md#вход-и-ошибки).

**Обоснование:** запрещать кавычки или искать слова `DROP` недостаточно: это ломает обычные описания, но не отделяет код от данных. Параметры сохраняют структуру SQL независимо от текста. Проверки длины и формата решают другие задачи; не заменяют параметризацию и полномочия D-02. Сообщение клиенту при ошибке не содержит SQL и реквизитов БД.

**Будущая проверка:** передать SQL-фрагменты в логин, ID и описание; проверить вход и чужую карточку, затем сравнить свои и чужие записи в БД. Ожидаем неверный вход 401, некорректный ID 400, допустимый текст сохранён буквально, нет доступа или изменений чужих данных. Повторить для всех новых запросов сообщений, заметок и переходов после их реализации.

**Ограничения:** появление динамической сортировки или названий таблиц потребует серверного списка разрешённых значений; SQL-параметр не заменяет идентификатор столбца.
