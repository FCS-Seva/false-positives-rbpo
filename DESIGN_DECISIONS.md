# Решения безопасности

## D-02. Проверка объекта, действия и состава ответа

**Контекст:** вошедший заявитель B может подставить номер обращения A; специалист S2 — номер назначения S1. Проверка только роли пропускает оба случая. Будущая заметка также может утечь в общей сериализации обращения. Связи: T-02, T-03, T-04 → SR-02, SR-03, SR-04.

**Решение:** идентичность берём из серверной сессии. При чтении запрос к БД включает предикат `author_id = user.id` для заявителя или `assignee_id = user.id` для специалиста. Тот же фильтр действует в списке. Чужой и отсутствующий номер дают одинаковый 404. DTO содержит только явно разрешённые поля; неизвестные поля входного JSON отклоняются. При создании автор берётся из сессии, состояние и время — из БД. Проверки выполняются на сервере при каждом запросе.

Целевая политика действий:

| Действие | Кто | Условие | Состав ответа / записи |
| --- | --- | --- | --- |
| Создать | Заявитель | Действительная сессия | Только тема и описание от клиента; начальное состояние `new` |
| Читать обращение | Автор или ответственный | Совпадает связь с объектом; любое состояние | Общие данные без внутренних заметок |
| Очередь (план) | Специалист | Только `new`, без ответственного | Только номер и время; содержание ещё закрыто |
| Принять (план) | Специалист | Свободное `new`, `expected_version=1` | Назначить текущего специалиста |
| Сообщение (план) | Автор / ответственный | Автор: `new` или `in_progress`; ответственный: `in_progress` | Автор и время от сервера |
| Заметка (план) | Ответственный | Запись только `in_progress`; чтение также после закрытия | Отдельный ресурс; доступ автора и S2 запрещён |
| Закрыть (план) | Ответственный | `in_progress`, непустое решение, актуальная версия | Добавить решение и событие, сохранить назначение |
| Открыть снова (план) | Автор | `closed`, непустая причина, актуальная версия | Добавить причину и событие; сохранить назначение |

**Обоснование:** скрытая кнопка или проверка роли в клиенте обходится прямым HTTP-запросом. Проверка связи с объектом в SQL ограничивает и карточку, и список. Раздельные DTO и ресурс заметок позволяют контролировать поля без фильтрации уже раскрытого ответа.

**Будущая проверка:** подготовить A/B/S1/S2, свободное и назначенное S1 обращение, заметку. Выполнить чтение карточки, списка, очереди и заметки каждым аккаунтом; подставить чужой номер и поля author/role/assignee/status. Ожидаем разрешение только по таблице, отсутствие текста заметки в любом ответе A/B/S2, очередь без темы и описания, неизменную БД при отказе. Повторить чтение после закрытия и открытия. Уже реализованная часть проверяется HTTP-тестами; очередь и заметки пока только план.

**Ограничения:** оператор БД доверенный и может обходить HTTP. Сейчас нет переназначения. При его добавлении политика и тесты должны пересматриваться.

## D-01. Пароли и отзываемые серверные сессии

**Контекст:** наличие заголовка не подтверждает личность; быстрый хеш позволяет дешёвый перебор копии БД. Связи: T-01, T-08 → SR-01, SR-08.

**Решение:** учебные роли готовит локальный seed. Пароли хранятся как Argon2id: 64 MiB, 3 прохода, p=1, случайная соль 16 байт, результат 32 байта. Алгоритм и параметры входят в сохранённую строку. Проверка допускает только выбранные параметры и длины, сравнивает результат за постоянное время. Неизвестный логин проходит такую же дорогую проверку фиктивного хеша. Одновременно допускаются четыре проверки, остальные запросы получают 429.

После успешного входа сервер выдаёт 32 случайных байта в base64url. База хранит SHA-256 токена, account_id и срок 8 часов; роль при каждом запросе читается из аккаунта. SHA-256 подходит для случайного 256-битного токена, но не для человеческого пароля. Выход удаляет текущую сессию. Повторный seed меняет пароли и отзывает сессии учебных аккаунтов, сохраняя обращения. Ошибка БД не даёт доступ. Ответы не кешируются; пароль и токен не пишутся в журналы.

**Обоснование и альтернативы:** Argon2id выбран для замедления перебора через память и вычисления. Параметры выше [минимального ориентира OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html); на целевом компьютере их ещё нужно измерить под нагрузкой. Выбрана серверная сессия, потому что немедленный выход и смена пароля требуют отзыва. Самодостаточный JWT уменьшает обращения к БД, но для немедленного отзыва всё равно нужна дополнительная серверная информация. Для небольшого локального API один запрос сессии проще. Bearer-токен выбран для CLI; браузерного интерфейса сейчас нет.

**Будущая проверка:** на A/B проверить правильный и неверный пароль, неизвестный логин, отсутствие/подмену токена, выход, срок сессии и отказ БД. Ожидаем 200 только для действительного входа, 401 для недействительной сессии, 503 при недоступной БД без личных данных. У одинакового пароля A/B хеши должны различаться, исходного пароля в базе нет. После seed прежние токены не работают, обращения остаются. Для будущего сетевого развёртывания измерить задержку и память, проверить TLS и лимиты повторных попыток; четыре слота ограничивают память, но не останавливают последовательный перебор.

**Ограничения:** сейчас HTTP разрешён только на loopback. Полученный токен даёт права до истечения/отзыва; безопасность клиента и ОС — допущение модели. Очистка истёкших строк сессий и полноценные лимиты входа будут нужны при долгом сетевом запуске.

## D-04. Параметризованный SQL и ограниченный ввод

**Контекст:** логин и тексты проходят от клиента до БД, а номер влияет на выбор объекта. Связь: T-07 → SR-07.

**Решение:** запросы написаны статически; значения передаются через `$1`, `$2` и следующие параметры pgx. Склейка SQL используется только для постоянных серверных фрагментов (список полей и предикат доступа), без пользовательского ввода. ID — положительный int64 из десятичных цифр; текст — UTF-8 без NUL, с пределом длины. JSON ограничен 32 KiB, неизвестные поля и дополнительные JSON-значения отклоняются. Допустимый текст с кавычками или SQL сохраняется как строка после стандартного JSON-декодирования, без SQL-интерпретации. Политика повторных ключей и Unicode описана в [API.md](API.md#вход-и-ошибки).

**Обоснование:** запрещать кавычки или искать слова `DROP` недостаточно: это ломает обычные описания, но не отделяет код от данных. Параметры сохраняют структуру SQL независимо от текста. Проверки длины и формата решают другие задачи; не заменяют параметризацию и полномочия D-02. Сообщение клиенту при ошибке не содержит SQL и реквизитов БД.

**Будущая проверка:** передать SQL-фрагменты в логин, ID и описание; проверить вход и чужую карточку, затем сравнить свои и чужие записи в БД. Ожидаем неверный вход 401, некорректный ID 400, допустимый текст сохранён буквально, нет доступа или изменений чужих данных. Повторить для всех новых запросов сообщений, заметок и переходов после их реализации.

**Ограничения:** появление динамической сортировки или названий таблиц потребует серверного списка разрешённых значений; SQL-параметр не заменяет идентификатор столбца.

## D-03. Атомарное назначение, версия и история переходов

**Контекст:** два специалиста могут принять одну запись, а проверка и изменение в разных запросах дают гонку. Сбой между состоянием и решением теряет историю. [Контрпример T-09](THREAT_MODEL.md#контрпример-t-09-и-уточнение-цепочки) показывает, что одинаковое состояние в двух циклах не означает актуальность команды. Связи: T-05, T-06, T-09 → SR-05, SR-06; назначение также влияет на SR-02.

**Статус:** механизм планируется. В текущей схеме уже есть `version=1`, ограничения состояния и назначения; команд переходов, таблиц сообщений/заметок/событий ещё нет.

**Решение:** клиент передаёт `expected_version` для принятия, закрытия и открытия. В одной транзакции сервер выполняет условный UPDATE и добавляет событие/решение/причину. Отказ или сбой записи события откатывает UPDATE. Количество изменённых строк обязательно проверяется. Версия увеличивается на один при каждом переходе; пользователь не назначает новую версию напрямую.

**Источник версии:** новое обращение создаётся с версией 1; разрешённые переходы не возвращают его в `new`, а сообщения не меняют версию состояния. Поэтому для принятия специалист передаёт `expected_version=1`, не читая закрытое ему содержание. Очередь остаётся минимальной: только номер и время. Для закрытия и повторного открытия текущая версия берётся из доступной карточки; ответ успешного перехода содержит новую версию. Пропущенная или неположительная версия даёт 400; несовпадение с текущей — 409 без изменений. Если появится возврат в `new` или другие изменения его версии, это правило нужно пересмотреть и согласовать выдачу версии в очереди с SR-02/D-02.

Пример выбранного принятия (планируемый SQL, параметры только сервер/проверенный ввод):

```sql
UPDATE tickets
SET assignee_id = $1, status = 'in_progress', version = version + 1
WHERE id = $2 AND status = 'new' AND assignee_id IS NULL AND version = $3
RETURNING id, version;
```

`$1` — текущий специалист из сессии, `$2` — номер, `$3` — ожидаемая версия (для принятия — 1). Для закрытия предикат дополнительно требует текущего ответственного и `in_progress`; для открытия — автора и `closed`. Роли и непустой текст проверяются до записи. Успех фиксируется только после COMMIT. Доступ к содержанию появляется после назначения, а проигравший не получает его в ответе.

История будет добавляться отдельными записями (автор/время/тип/текст/обращение), без замены прежнего решения. Назначение сохраняется при закрытии и открытии. Для сообщения/заметки транзакция блокирует строку обращения, проверяет полномочия и разрешённое состояние, затем вставляет запись: параллельное закрытие не может обойти эту проверку. Версия описывает переходы состояния; произвольный повтор старого сообщения потребует отдельного правила идемпотентности, сейчас оно не заявлено.

**Сравнение альтернатив:**

| Вопрос | Условный UPDATE (выбран для переходов) | SELECT FOR UPDATE → проверка → UPDATE |
| --- | --- | --- |
| Два принимающих | Один UPDATE меняет свободную строку; второй после ожидания видит иной предикат и не меняет строку | Второй ждёт блокировку; обязан заново проверить состояние после чтения |
| Где проверка | Роль проверена сервером; связь, состояние и версия находятся в WHERE изменения | Все проверки в коде после получения блокировки, до записи |
| Риск реализации | Забытый предикат или игнорирование нуля строк даёт ошибочный успех | Проверка до блокировки, забытая повторная проверка или ранний COMMIT снова открывает гонку |
| Задержавшаяся команда другого цикла | Обязательно `version = expected_version`; один предикат статуса недостаточен | Та же проверка версии обязательна; блокировка сама не определяет актуальность |
| История / сбой | UPDATE и INSERT события в общей транзакции, иначе возможен разрыв | То же требование; блокировка без транзакции истории недостаточна |
| Сложная логика | Короткий предикат перехода хорошо читается; несколько связных объектов усложняют запрос | Удобно разбирать несколько правил в коде, но блокировка держится дольше |

Для трёх коротких переходов выбран условный UPDATE: меньше промежутков между проверкой и записью, правила видны в одном запросе. `READ COMMITTED` в PostgreSQL подходит: конкурирующий UPDATE ждёт строку и [повторно проверяет WHERE на обновлённой версии](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED). При варианте с [блокировкой строки](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS) всё равно нужны проверки статуса и версии. Повышение уровня изоляции само по себе не распознаёт последовательно пришедшую старую команду.

**Условие пересмотра:** если переход начнёт одновременно менять несколько связанных объектов и общий инвариант станет трудно выразить коротким предикатом, заново сравним условный UPDATE с явной блокировкой всех участвующих строк и проверкой правил в коде. Учитываем длительность блокировок и единый порядок их захвата; ожидаемая версия и общая транзакция истории нужны в обоих вариантах.

**Будущие проверки:**

- **Назначение:** два подключения и общий барьер запуска S1/S2 принимают одно `new` с `expected_version=1`, получив из очереди только номер и время. Один успех, один 409; версия 2, один ответственный, одно событие, нет записи в очереди. Проигравший не читает содержание; повторное принятие не меняет назначение.
- **Целостность:** после допустимого UPDATE искусственно оборвать вставку события/решения до COMMIT. После отката состояние, версия и вся история прежние; клиент не получает успех. Проверить запрет пустого решения/причины и неправильных ролей без изменений.
- **Источник версии:** отсутствующая/неположительная версия даёт 400; принятие нового обращения с положительной версией 2 вместо 1 даёт 409. Состояние, назначение и история не меняются. После успешного принятия возвращаются версия 2 и доступ к карточке; закрытие и открытие используют прочитанную версию.
- **Старый цикл:** выполнить сценарий T-09 обычными переходами: `new v1 → in_progress v2 → closed v3 → in_progress v4`. Старое закрытие версии 2 получает 409 без изменений; свежее закрытие версии 4 даёт `closed v5` и второе решение.
- **Сообщение и закрытие:** задержать запись сообщения/заметки после блокировки, параллельно закрыть. Итог соответствует одному порядку: сообщение целиком до закрытия либо отказ записи после закрытия; нет записи, принятой на устаревшей проверке состояния.
- **При пересмотре для нескольких объектов:** после появления такого перехода запустить конкурирующие изменения связанных строк. Успех должен сохранять общий инвариант; сбой одной записи откатывает все изменения и историю. Проверить единый порядок блокировок, завершение конкурирующих запросов и обработку отката при взаимной блокировке. Это условная будущая проверка расширения, которого сейчас нет.

**Ограничения и последствия:** нет переназначения, удаления и автоматического повторения команды с новой версией. При нескольких блокируемых объектах понадобится единый порядок захвата. Сравнение вариантов и будущие тесты не объявляются результатом проверки текущего API.
