# Локальный запуск и проверки

Нужны Go **1.26+** и запущенный PostgreSQL **18** на `127.0.0.1:5432`. Добавьте утилиты `createuser` и `createdb` в PATH. Все трое используют приведённую ниже схему: роль `ek1_app`, рабочая БД `helpdesk_ek1` и отдельная тестовая БД `ek1_test_suite`. API написан на `net/http`, драйвер БД — `pgx/v5/stdlib`; зависимости закреплены в `go.mod`/`go.sum`.

## Подготовка БД

Один раз выполните стандартные команды PostgreSQL. Здесь `postgres` — административная роль вашего локального сервера; замените её, если при установке использовано другое имя (например, имя пользователя macOS в Homebrew).

```sh
createuser -h 127.0.0.1 -p 5432 -U postgres --pwprompt ek1_app
createdb -h 127.0.0.1 -p 5432 -U postgres --owner=ek1_app helpdesk_ek1
createdb -h 127.0.0.1 -p 5432 -U postgres --owner=ek1_app ek1_test_suite
```

Первая команда запрашивает новый пароль роли `ek1_app`; сохраните его локально. Роль приложения владеет учебными БД и не является суперпользователем. Справка: [createuser](https://www.postgresql.org/docs/18/app-createuser.html), [createdb](https://www.postgresql.org/docs/18/app-createdb.html).

## Запуск API

Из корня репозитория выполните команды, заменив `DB_PASSWORD` и `LOCAL_ACCOUNT_PASSWORD` своими значениями. Спецсимволы пароля БД в URL нужно кодировать; для учебной локальной установки удобно выбрать пароль из букв и цифр. Пароли и токены не коммитьте.

```sh
export DATABASE_URL='postgres://ek1_app:DB_PASSWORD@127.0.0.1:5432/helpdesk_ek1?sslmode=disable'
export SEED_PASSWORD='LOCAL_ACCOUNT_PASSWORD'
go mod download
go run ./cmd/seed
go run ./cmd/server
```

`SEED_PASSWORD` должен содержать 12–256 байт. Seed применяет миграцию и создаёт `requester_a`, `requester_b`, `specialist_1`, `specialist_2` с этим учебным паролем. Повторный seed обновляет пароли и отзывает сессии, сохраняя обращения. **Выполняйте seed при остановленном API:** одновременная смена пароля и вход не входят в текущую демонстрацию.

API слушает `http://127.0.0.1:8080`. Можно изменить порт через `LISTEN_ADDR=127.0.0.1:8081`; открытый сетевой адрес отклоняется. Для удалённого развёртывания нужны отдельная настройка TLS и лимиты входа.

В другом терминале проверьте запущенный процесс и соединение с БД:

```sh
curl -fsS http://127.0.0.1:8080/health
curl -fsS http://127.0.0.1:8080/ready
```

Ожидаются HTTP 200 и соответственно `{"status":"ok"}` и `{"status":"ready"}`. При другом порте API замените его в командах.

## Проверки

Из корня репозитория задайте URL **отдельной тестовой БД** и запустите полный набор:

```sh
export TEST_DATABASE_URL='postgres://ek1_app:DB_PASSWORD@127.0.0.1:5432/ek1_test_suite?sslmode=disable'
go test ./... -count=1
go vet ./...
```

**Тесты очищают accounts, sessions и tickets в тестовой БД.** Имя должно начинаться с `ek1_test_`; нельзя указывать рабочую `helpdesk_ek1`. Без `TEST_DATABASE_URL` интеграционные тесты пропускаются, выполняются только unit-тесты паролей. HTTP-тесты работают с настоящей PostgreSQL; аккаунты готовит общий seed.

| Тест | Что проверяет | Связи |
| --- | --- | --- |
| `TestSaltAndVerification`, `TestMalformedHashesFailClosed` | Соли, верный/неверный пароль, повреждённые хеши | T-08 → SR-08 → D-01 |
| `TestHTTPAuthentication` | Вход, серверная роль, хеш токена, истечение и отзыв сессии | T-01/T-07 → SR-01/SR-07 → D-01/D-04 |
| `TestHTTPTickets` | Создание, доступ A/B/S1/S2, скрытые поля, буквальный SQL-текст, полный список | T-02/T-04/T-07 → SR-02/SR-04/SR-07 → D-02/D-04 |
| `TestHTTPRejectsInputWithoutWrites` | Неверные JSON/ID, пределы длины, подмена полей; данные не меняются | T-04/T-07 → SR-04/SR-07 → D-02/D-04 |
| `TestSeedRevokesSessionsPreservesTickets` | Новый пароль, отзыв сессий, разные соли, сохранение обращений | T-01/T-08 → SR-01/SR-08 → D-01 |
| `TestHTTPDatabaseFailureDoesNotGrantAccess` | Отказ БД даёт 503 без раскрытия SQL и доступа | SR-01 → D-01 |

Очередь, заметки, гонка принятия, история и старое закрытие T-09 — будущие проверки D-02/D-03. Назначение в тестовой БД задаёт фикстура; проверка чтения не доказывает безопасность ещё отсутствующей команды принятия.

## Ручной пример и перезапуск

Отправьте `POST /login` с JSON `{"login":"requester_a","password":"<ваш SEED_PASSWORD>"}`. Передайте полученный `token` в `Authorization: Bearer <token>` и `Content-Type: application/json` при `POST /tickets` с `{"title":"Не работает Wi-Fi","description":"Сеть видна, соединение не устанавливается"}`. Прочитайте `GET /tickets` и `GET /tickets/<id>`. Второй заявитель получает 404 для того же ID. Специалист не создаёт обращения и читает только назначенные ему. Контракт: [API.md](API.md).

Сохраните ID, остановите API через Ctrl+C и снова выполните `go run ./cmd/server` с тем же окружением. Войдите и прочитайте обращение: данные должны сохраниться. Seed для перезапуска не требуется. PostgreSQL останавливается и запускается средствами вашей установки; остановка сохраняет данные.

503 на `/ready` означает недоступную БД: проверьте сервер, порт и `DATABASE_URL`. Если таблицы или аккаунты ещё не готовы, остановите API и выполните seed. При занятом порте API задайте другой `LISTEN_ADDR`. Сервер не печатает URL БД, пароль или токен в журналы.
